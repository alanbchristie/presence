User guide

What Presence does, how to set it up, and how it works.

What it is for

Presence makes an empty building look occupied. Each presence record switches between on and off at random times, but only during a daily window, for example from an hour before sunset until half past eleven.

Presence does not control any devices itself. It publishes each presence's current state through a small API, and a home-automation system such as Home Assistant reads that state and switches a real light (or anything else) to match. Because the on and off periods change every time, the lights never follow the same pattern two nights in a row.

There are three kinds of record, set up in this order:

  1. Locations say where presences are, which sets their timezone and sunset/sunrise times.
  2. Access keys are the secrets a home-automation system uses to read a presence's state.
  3. Presences are the individual on/off schedules, each at a location and protected by a key.

Locations

A location is a named place, such as a house. Settings that depend on where a presence is are set on its location, so all the presences at one place share them:

  • Timezone is an IANA name such as Europe/London. Wall-clock window times, and the times shown for each presence, use this timezone.
  • City is a city from the built-in astronomical database, used to work out sunset and sunrise. You only need it if a presence at this location has a window edge set relative to sunset or sunrise.
  • Position is optional. It sets where the location's marker appears on the Map, instead of at its city. Enter it as a latitude/longitude pair or a What3Words address.

The Default location always exists. Presences created without a location are placed there. It cannot be renamed or deleted, and no location can be deleted while presences use it.

Access keys

An access key is a named secret. When the value is first created it is a random string, and a home-automation system must send it with each request to read a presence's state. Every presence is protected by exactly one key.

Ideally, give each presence its own access key. If a key is ever exposed, only that one presence is affected, and you can regenerate or replace it without changing anything else. Where that is not practical, presences at the same location can share a key, but a key can never be used at more than one location.

You can create a key on the Access keys page, or while adding a presence by typing a new key name on the presence form. Regenerate replaces a key's value, and the old value stops working straight away, so remember to update whatever reads it. A key that is in use cannot be deleted.

Presences

Add a presence from the Presences page. Its settings are:

Identifier
A unique, URL-safe name such as living-room, made of lowercase letters, digits and hyphens. It is part of the presence's API address.
Name
A readable label, such as "Living room lamp".
Enabled
Untick to pause a presence without deleting it. A paused presence is left in whatever state it was in.
Location
Where the presence is. If you leave it blank, the Default location is used.
Access key
Choose an existing key, or type a name to create a new one.
Window

When the presence is active each day. Each edge (Open and Close) can be written in one of two ways:

  • HH:MM is a wall-clock time in the location's timezone. For example, 23:30.
  • +HH:MM or -HH:MM is an offset from sunset for Open, or from sunrise for Close. For example, -01:00 opens an hour before sunset. The location must have a city for this.

The sign is what matters: +00:00 is exactly at sunset (or sunrise), while 00:00 is midnight. If Close is at or before Open, the window runs past midnight.

On / Off
The shortest and longest time for each on and off period, written as HH:MM:SS. The minimum is one minute, and Max must not be less than Min. Each period is a random length between the two, so a wider range gives a less predictable pattern.

Duplicate on a presence's page opens a new presence with the same settings. You only need to give it a new identifier and name.

Using a presence

Each presence's current state is available from the API. Send the presence's access key value in the X-API-Key header: 

curl -H "X-API-Key: <key value>" {{ api_example }}

The JSON reply includes "state" ("on" or "off"), and when the state will next change. If a request has a missing or wrong key, or names a presence that does not exist, it receives the same 403 response. After repeated failures, requests from that address are temporarily refused.

A presence's page links to View as JSON and to View as HA Binary Sensor, which is a ready-made Home Assistant sensor (see Home Assistant below). The Map shows each location's current state, with the parts of the world where it is night shaded.

Home Assistant

Using a presence in Home Assistant takes two steps. First, add a binary sensor that reads the presence's state. Then add an automation that switches a light when that sensor changes.

1. Add the sensor

Open the presence's page and choose View as HA Binary Sensor. It gives you the complete YAML, including this server's address and the presence's real access key. Paste it into Home Assistant's configuration.yaml, adding the entry under any existing binary_sensor: heading rather than repeating the heading. Then use Developer tools → YAML to check the configuration, and restart Home Assistant.

  • To keep the key value out of configuration.yaml, move it to secrets.yaml and refer to it with X-API-Key: !secret presence_living_room_key.
  • Home Assistant reads the sensor every 30 seconds by default. Adding scan_interval: 60 to the sensor makes it read less often. The light then changes up to a minute after Presence does, which does no harm when the times are random anyway.

The sensor is named Presence Simulator (<name>), so a presence named "Living room" becomes binary_sensor.presence_simulator_living_room. To confirm the exact ID, search for "Presence Simulator" under Settings → Devices & services → Entities.

2. Add the automations

The sensor only reports the state. Automations make a light follow it, and the simplest way is to use two: one that switches the light on and one that switches it off. Go to Settings → Automations & scenes → Create automation → Create new automation, choose Edit in YAML from the ⋮ menu, and paste in each example below. Then change the entity IDs to match your own.

The On automation:

alias: Living room lamp (On) [Living room simulator]
triggers:
  - trigger: state
    entity_id: binary_sensor.presence_simulator_living_room
    from: ["off", unavailable, unknown]
    to: "on"
conditions:
  - condition: state
    entity_id: input_boolean.away
    state: "on"
  - condition: state
    entity_id: input_boolean.living_room_override
    state: "off"
actions:
  - action: light.turn_on
    target:
      entity_id: light.living_room_lamp
    data:
      brightness_pct: 40
      color_temp_kelvin: 3000
mode: single

The Off automation:

alias: Living room lamp (Off) [Living room simulator]
triggers:
  - trigger: state
    entity_id: binary_sensor.presence_simulator_living_room
    from: ["on", unavailable, unknown]
    to: "off"
conditions:
  - condition: state
    entity_id: input_boolean.living_room_override
    state: "off"
actions:
  - action: light.turn_off
    target:
      entity_id: light.living_room_lamp
mode: single
  • Triggers: each automation runs only when the sensor becomes on (or off). This includes the sensor recovering from unavailable or unknown, for example after Home Assistant restarts or loses contact with Presence for a while. Losing contact never triggers anything, so a network problem does not switch your lights.
  • Away: input_boolean.away is a Toggle helper that you create under Settings → Devices & services → Helpers and switch on when you leave, so the simulation only switches the light on while you are away. The Off automation deliberately leaves this condition out. A light the simulation switched on then still goes off at the end of its on period, even if you have come home in the meantime.
  • Override: input_boolean.living_room_override is a second Toggle helper, one per light. Switch it on to take manual control of the light, and both automations will leave it alone.
  • More conditions: add any other conditions to the On automation, for example a sensor that is off on public holidays.
  • Actions: brightness_pct and color_temp_kelvin make a lamp look lived-in rather than floodlit, so drop them for a light that does not support them. For a smart plug or relay, use switch.turn_on and switch.turn_off. When built in the visual editor, the target is often a device_id. That works just as well, but an entity_id is easier to read.

Naming each pair "Light (On) [Presence simulator]" keeps related automations together in Home Assistant's list. For a more convincing effect, give each room its own presence and pair of automations, so the rooms do not all switch at the same moment.

Under the hood

Presence runs as two parts. The web application provides these pages and the API. A separate background process, the runner, wakes whenever a state change is due (and at least every 30 seconds) and decides whether each enabled presence should change state. Only one runner ever drives the database, so each presence has exactly one schedule.

For each presence, the runner follows these rules:

  • Outside its window, a presence is always off.
  • When the window opens, the presence does not switch on at the opening time. It starts with a random off period, so switching on never happens at a predictable moment.
  • During the window it alternates between random on and off periods, each chosen between the Min and Max you set.
  • An on period that would run past the window's close is cut short at the close.

The runner saves each presence's state, when that state started, and when the next change is due. These pages and the API report those saved values, so what you see is exactly what a home-automation system reads.
